## Verifying releases

`.github/workflows/release.yml` publishes signed binaries and a signed
container image when a `vX.Y.Z` tag is pushed. This section says what is
published, how to verify it before use, how a release is cut and what the
process does not guarantee.

Status: No release has been published yet. The workflow is statically tested
(`test/release_test.go`, actionlint) and its image build, scan and file
listing were run locally; it has not run on GitHub. Its design is that of the
sibling project fleet-in-a-repo, whose release workflow did run on GitHub.

### What is published

| Artifact | Where | Contents |
|---|---|---|
| Binaries | GitHub Release `vX.Y.Z`: `k8s-mcp_vX.Y.Z_<os>_<arch>.tar.gz` for `linux_amd64`, `linux_arm64`, `darwin_amd64`, `darwin_arm64` | static `k8s-mcp` (`CGO_ENABLED=0`, `-trimpath`, version stamped with `-X main.version`), `LICENSE`, `README.md` |
| Checksums | same Release: `SHA256SUMS` | sha256 of the four archives |
| Signatures | same Release: `<file>.sigstore.json` for every archive and for `SHA256SUMS` | keyless cosign bundles (certificate, signature, Rekor inclusion proof) |
| Image | `ghcr.io/astawiany/k8s-mcp:vX.Y.Z` | linux/amd64; distroless `static-debian12:nonroot` base (pinned by digest) plus `/k8s-mcp`; runs as 65532:65532; OCI labels `source`, `revision`, `version`, `licenses=MIT`, `title` |
| Image attestations | attached to the image index | SPDX SBOM and SLSA provenance (`mode=max`) generated by the pinned BuildKit |
| Image signature | next to the image in the registry, logged in Rekor | keyless cosign signature of the image index digest |

Before anything is published the workflow fails on: a vulnerable Go function
the code actually calls (govulncheck, per binary platform and in the image
builder), a fixable HIGH or CRITICAL vulnerability in the image, any secret in
the image or the repository, a HIGH or CRITICAL Dockerfile misconfiguration
(Trivy). The image is pushed by digest only, with no tag; the job checks that
the pushed image has the same config digest as the scanned one, signs and
verifies that digest, and only then creates the version tag and checks that it
resolves to the signed digest. The GitHub Release is created last, after the
image is signed and after every archive and `SHA256SUMS` was signed and
verified.

### Verify before use

Requirements: `cosign` 3.x, `docker` with buildx, `jq`, `sha256sum` (macOS:
`shasum -a 256 --ignore-missing -c SHA256SUMS`).

```sh
TAG=v0.1.0
IDENTITY="https://github.com/astawiany/k8s-mcp/.github/workflows/release.yml@refs/tags/$TAG"
ISSUER=https://token.actions.githubusercontent.com
```

The identity is the exact one of `release.yml` of this repository running for
that tag. A signature made by any other workflow, branch, tag or repository
does not match it.

Binaries: download the archive for your platform, `SHA256SUMS` and both
bundles from the Release page, then:

```sh
cosign verify-blob --bundle SHA256SUMS.sigstore.json \
  --certificate-identity "https://github.com/astawiany/k8s-mcp/.github/workflows/release.yml@refs/tags/$TAG" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com SHA256SUMS
cosign verify-blob --bundle "k8s-mcp_${TAG}_linux_amd64.tar.gz.sigstore.json" \
  --certificate-identity "$IDENTITY" --certificate-oidc-issuer "$ISSUER" \
  "k8s-mcp_${TAG}_linux_amd64.tar.gz"
sha256sum --ignore-missing -c SHA256SUMS
tar -xzf "k8s-mcp_${TAG}_linux_amd64.tar.gz"
"k8s-mcp_${TAG}_linux_amd64/k8s-mcp" --version   # prints $TAG
```

Image: resolve the tag to a digest once, verify that digest, then use only the
digest (tags on GHCR are mutable).

```sh
DIGEST="$(docker buildx imagetools inspect "ghcr.io/astawiany/k8s-mcp:$TAG" --format '{{json .Manifest}}' | jq -r .digest)"
cosign verify "ghcr.io/astawiany/k8s-mcp@$DIGEST" \
  --certificate-identity "https://github.com/astawiany/k8s-mcp/.github/workflows/release.yml@refs/tags/$TAG" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
docker run --rm "ghcr.io/astawiany/k8s-mcp@$DIGEST" --version
```

SBOM and provenance (both are listed in the signed index, so the image
signature covers them):

```sh
docker buildx imagetools inspect "ghcr.io/astawiany/k8s-mcp@$DIGEST" --format '{{json .SBOM}}' | jq '.SPDX.packages[].name'
docker buildx imagetools inspect "ghcr.io/astawiany/k8s-mcp@$DIGEST" --format '{{json .Provenance}}' | jq '.SLSA'
```

The provenance names the source repository, the commit, the build arguments
and the base image digests. The Release notes of each version repeat these
commands with the tag and image digest filled in.

### Threat model of releases

1. Who can publish: a `v*` tag runs `release.yml`. The `release-tags` ruleset
   (`scripts/protect-branch.sh`) lets only admins create, move or delete `v*`
   tags; the `image` and `release` jobs wait for a `release` Environment
   reviewer; `verify` refuses a commit that is not on `main` or a version that
   already exists.
2. The identity names the file and the tag, not the code: a writer who could
   push a `v*` tag on a branch with a modified `release.yml` (no `verify`, no
   Environment) would get a matching signature. The ruleset is the control
   that matters; `verify` and the Environment bind only the reviewed
   `release.yml` on `main`.
3. A compromised tag push cannot overwrite a published version (absence is
   checked in `verify` and again right before every write) and cannot publish
   without an Environment approval; it can publish a new version from `main`
   if approved.
4. Tags on GHCR are mutable: resolve once, verify, and consume by digest.
5. No reproducible-build proof: nobody rebuilds independently and compares,
   although builds are deterministic for a commit (no VCS stamping, fixed
   timestamps, `-trimpath`).
6. No SLSA level is claimed beyond the provenance attestation, which BuildKit
   produces inside the same job, not an isolated builder.
7. The scans are point-in-time on the release day; rescan by digest
   (`trivy image ghcr.io/astawiany/k8s-mcp@<digest>`) for later CVEs.
8. `GITHUB_TOKEN` is the only credential (no long-lived registry or signing
   keys); signing identities and digests are public in Rekor.

### Release procedure

0. Once per repository: `scripts/protect-branch.sh --repo astawiany/k8s-mcp`
   (preview with `--dry-run`; see [.github/README.md](../.github/README.md))
   for branch protection, the `release` Environment and the tag ruleset.
1. Create the tag from `main` (only admins can, through the ruleset):
   `git tag v0.1.0 origin/main && git push origin v0.1.0`.
2. `verify` and `build` run; approve the `release` Environment gate for
   `image`, then for `release` (each job asks for its own approval). The job
   summaries list the image digest.
3. Verify the image and the binaries with the commands above.
4. First release only: make the package public (next section).

A version is never overwritten. A half-finished release (a job failed after
something was pushed) is not re-run: re-runs stop at the absence checks. Bump
the version and tag again. An image pushed by digest but never tagged or
signed is not a release; delete it from the package page if you like.

### GHCR packages

- The first push creates `ghcr.io/astawiany/k8s-mcp` as a private package
  owned by `astawiany`. The image's `org.opencontainers.image.source` label
  links it to this repository.
- Making it public is a manual step, done only AFTER the first release was
  verified: GitHub > your profile > Packages > `k8s-mcp` > Package settings >
  Danger Zone > Change visibility > Public. It cannot be undone for that
  package.
- Check visibility (token with `read:packages`):
  `gh api users/astawiany/packages/container/k8s-mcp --jq .visibility`.

### Not covered

- The image is linux/amd64 only; arm64 users run the binaries.
- The SBOM is produced by the pinned `docker/buildkit-syft-scanner` image
  (`SBOM_GENERATOR_IMAGE` in `versions.env`); its accuracy is that tool's.
- The binary archives carry no SBOM or provenance of their own.
